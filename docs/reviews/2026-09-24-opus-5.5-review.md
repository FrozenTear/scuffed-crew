## High

### H1 (Deploy / API): `PRODUCTION=1` does not stop an in-memory DB + seeded admin + `/api/dev/login`

- Where: `crates/server/src/main.rs:93-106` (`is_dev = SURREALDB_URL.is_err()`,
  then `connect_memory()` + `seed_dev_data`), `crates/site-server/src/lib.rs:176-189`
  (registers `/api/dev/login` when `SURREALDB_URL` is unset),
  `crates/site-server/src/routes/dev.rs:11-64` (fixed token
  `dev-session-token-do-not-use-in-production`).
- Impact: dev mode is gated only on `SURREALDB_URL` being unset. `PRODUCTION`
  is never consulted on this path, and `connect_memory()` skips the remote
  `assert_remote_production_policy` / `ENCRYPTION_KEY` refusal. A "production"
  process launched with `SURREALDB_URL` unset (dropped from the env, a typo, a
  `cargo run` with only `PRODUCTION=1`) boots an ephemeral DB, seeds admin
  `devadmin`, and serves `GET /api/dev/login`, which hands anyone who can reach
  the port a working admin session. Data silently does not persist across
  restart.
- Repro (confirmed locally): start `scuffed-server` with `PRODUCTION=1` and no
  `SURREALDB_URL`; `curl -i /api/dev/login` returns `303` with
  `set-cookie: sc_session=dev-session-token-...`; that cookie is admin at
  `/admin/`.
- Reasoning on blast radius: the blessed compose hardcodes
  `SURREALDB_URL: ws://surrealdb:8000` (`compose.yml:65`), so the normal VPS
  install is safe, and an empty string `SURREALDB_URL=""` parses as `Ok("")` and
  takes the remote path (fails closed). The hole is specifically the unset case
  under a production intent.
- Fix direction: when `is_production_env()` (or a new explicit flag), refuse to
  boot on the in-memory path, never seed, and never register `/api/dev/login`.
  Treat blank `SURREALDB_URL` as unset for that refusal. Independently confirmed
  by two sub-reviewers and by the local run.

### H2 (API): unpublished (draft) articles are readable anonymously by slug

- Where: `crates/site-server/src/routes/articles.rs:68-91` (`get_article`, no
  auth extractor), `crates/db/src/queries/articles.rs:117-133`
  (`get_article_by_slug` runs `SELECT * FROM article WHERE slug = $slug LIMIT 1`
  with no `published = true` filter), route registered at
  `crates/site-server/src/lib.rs:416-419` (outside the public rate governor).
- Impact: `list_published_articles` correctly filters `published = true`, but
  the by-slug detail endpoint does not. Anyone who learns or guesses a draft
  slug (slugs are human-readable, e.g. `internal-roadmap`) gets the full
  `content_markdown` of an unpublished article, anonymously and unthrottled.
- Repro: officer creates but does not publish an article with slug `x`;
  anonymous `GET /api/articles/x` returns `200` with the body and
  `"published": false`.
- Fix direction: public get requires `published = true` (else 404); add a
  separate officer/admin loader for any-status reads used by the admin editor.

### H3 (Deploy): backups omit `data/secrets.env` / `ENCRYPTION_KEY`, so restored encrypted data is unrecoverable

- Where: `scripts/backup.sh:128-148` (restic paths are the SurrealDB logical
  export + `surrealdb-data` + `uploads-data` + optional `strfry-data` only),
  `scripts/restore.sh` (no secret restore), `docs/deploy.md:21-26,367-376`.
- Impact: `data/secrets.env` holds `ENCRYPTION_KEY` (and DB passwords). The DB
  export and volume both contain the AES-GCM-sealed Nostr secret keys, OAuth
  provider ids, and DM bodies. None of it decrypts without `ENCRYPTION_KEY`. If
  the host disk is lost or rebuilt and the operator did not separately copy
  `secrets.env`, a "successful" restic restore yields permanently unreadable
  secret material. This is the exact disaster backups exist to prevent, so it is
  rated High even though it requires host loss.
- Fix direction: include `secrets.env` in an encrypted restic repo (or a
  separate offline secret store), and document restoring secrets before starting
  the app. `install.sh`/`update.sh` correctly never regenerate `ENCRYPTION_KEY`
  (verified), so the key is stable; it simply is not backed up.

## Medium

### M1 (API): strategy WS global connection cap does not count un-joined sockets

`crates/server/src/routes/ws.rs:49-52,110-117` reject the upgrade only when
`RoomManager::global_connection_count() >= 256`, but that counter is incremented
only inside `join_room` (`crates/server/src/collab/room.rs:139-160`). A client
(including an anonymous one, since the upgrade does not require auth) can open
many sockets and never send `JoinRoom`; each lives up to 120s
(`WS_IDLE_TIMEOUT_SECS`). Authenticated/near-anonymous FD/task/memory DoS that
bypasses the advertised cap. Fix: count accepted upgrades (or live
`handle_socket` tasks) separately and refuse on that counter.

### M2 (API): collab broadcasts before DB persist; REST bulk save races WS edits

`try_spawn_persist` returns as soon as the task is spawned and the handler then
broadcasts (`crates/server/src/routes/ws.rs:311-327,359-381`;
`crates/server/src/collab/room.rs:238-258`); persist errors are only logged.
Peers apply edits that may never land in SurrealDB, and a concurrent REST
`save_full_strategy` (`crates/db/src/queries/strategies.rs:347-371`) can
overwrite WS read-modify-write with no shared version token. `confirms parked
B6-remainder` (`docs/security-quality-review-fix-list.md`). Fix: ack/broadcast
after persist (or a versioned CAS) and route REST bulk save through the same
per-strategy lock/version.

### M3 (API / Deploy): SSRF via admin-set `extra_relay_urls` (no host allowlist)

`parse_extra_relay_urls` only requires a `ws://`/`wss://` prefix
(`crates/site-server/src/routes/forum.rs:756-768`); forum fan-out then dials
each via `publish_event_oneshot` -> `tokio_tungstenite::connect_async`
(`crates/chat/src/nostr/relay.rs:216-218`) with no block on loopback, RFC1918,
link-local (`169.254.169.254`), or docker DNS. A malicious/compromised admin can
make the server open WebSockets to internal services (`ws://surrealdb:8000`,
`ws://127.0.0.1:8000`) on every forum publish. Admin-only, hence Medium. Fix:
allowlist public hosts / deny private + link-local + metadata; prefer env-only
relay config.

### M4 (API): `dm_sync` is expensive and not rate-limited

`crates/site-server/src/routes/nostr.rs:1696-1744` opens a one-shot relay
WebSocket, pulls up to 500 gift wraps, and decrypts them server-side on every
call, with no `enforce_nostr_rate_limit` (unlike `dm_send`/challenge/export).
Authenticated relay + CPU DoS that multiplies across members. Extends
`NOSTR-006`. Fix: apply an Interactive (or dedicated) `RateClass` and reuse a
shared relay connection.

### M5 (API): ICS field injection via unescaped CR / TZID / DESCRIPTION

`crates/site-server/src/calendar.rs:64-70` `escape_ical` escapes `\`, `;`, `,`,
`\n` but not `\r`, and `event.timezone` is interpolated raw into
`DTSTART;TZID=...`/`DTEND;TZID=...` (`:30-43`) while `team_id` is raw in
`DESCRIPTION` (`:56-58`). Officer-authored event fields flow into the public
`/api/calendar/all.ics`. A crafted `timezone` (or a `\r` in a text field) can
inject extra iCalendar properties for every subscriber. Fix: strip/replace
`\r`/`\n`, escape TZID and DESCRIPTION, and reject control chars on
create/update (`crates/site-server/src/routes/events.rs:67-85`).

### M6 (API): private-event RSVPs exposed without auth (IDOR by event id)

`GET /api/events/{id}/rsvps` and `.../rsvp-summary`
(`crates/site-server/src/routes/rsvps.rs:42-70`) have no extractor and never
check the event is public/active. Anonymous listing filters `is_public`, but a
known event id bypasses that, revealing who RSVP'd to a private practice. Fix:
require `is_public` (and active) for anonymous reads, or require `OrgMember`.

### M7 (API): public member profile serves inactive/banned members by id

`public_member_profile` (`crates/site-server/src/routes/public.rs:412-436`)
loads via `get_member_safe(&id)` with no `is_active` filter, while the public
list uses `is_active = true`. A banned/deactivated member's bio, socials, game
accounts, and team links stay public if the id is known. Fix: 404 when
`!is_active` (and optionally when suspended/banned).

### M8 (API): draft tournaments enumerable without auth

`GET /api/tournaments` and `GET /api/tournaments/{id}`
(`crates/site-server/src/routes/tournaments.rs:74-113`) have no extractor and
the status filter accepts `draft`. Unreleased tournament names/rules/participant
planning are visible to the internet. Fix: public list/detail restricted to
non-draft, or require `OrgMember` for draft.

### M9 (API): poll `close_at` is never enforced on vote

`vote_poll` (`crates/db/src/queries/polls.rs:154-166`) checks `is_active` only;
the scheduled `close_at` (stored at create, `:93-101`) is ignored until someone
manually deactivates the poll, so a "closed" poll keeps accepting votes. Extends
the `DB-003` hardening (is_active/allow_multiple were fixed). Fix: reject when
`close_at <= now`.

### M10 (API): non-atomic bracket generation

`crates/db/src/queries/tournaments.rs:985-1079` deletes an existing bracket then
creates many rounds/matches with no transaction or generation lock; a concurrent
double-click or a crash mid-run leaves a partial/corrupt bracket. `confirms
parked B8`. Fix: single transaction or a generation lock + status CAS; refuse if
a bracket already exists unless forced.

### M11 (Tracker / API): `personal_match (member_id, session_id)` index is not UNIQUE

`crates/db/src/migrations.rs:623-624` defines `pm_session_idx` as non-unique,
but the upsert keys on `(member_id, session_id)`
(`crates/db/src/queries/personal_stats.rs:100-157`). Concurrent daemon retries
can create duplicate rows for one session, inflating aggregates/leaderboards.
Fix: make the index UNIQUE on `(member_id, session_id)` and keep the upsert.

### M12 (API): many unauthenticated reads remain outside the rate governor; unbounded `wiki` offset

The public governor (`crates/site-server/src/lib.rs:105-174`) now covers
`/api/public/*`, calendar ICS, `/.well-known/nostr.json`, and the setup/provider
probes, but wiki, articles, announcements, tournaments, forum reads,
teams/roster/games, RSVP reads, and team matches are still unauthenticated and
unthrottled; `wiki.rs:40` also accepts an unbounded `offset`. One IP can amplify
DB load. `INCOMPLETE FIX of NS2-6` (calendar/ICS/NIP-05 done; the rest not).
Fix: nest the remaining anonymous reads under the same governor and clamp
`offset`.

### M13 (Deploy / API): no Content-Security-Policy header

`crates/server/src/main.rs:22-60` sets nosniff, `X-Frame-Options: DENY`,
referrer-policy, permissions-policy, and HSTS, but no CSP; `deploy/Caddyfile`
adds none either (confirmed absent on `ow.scuffedcrew.no` and locally).
Clickjacking is only partly covered by `X-Frame-Options`; an XSS anywhere in the
admin SPA has no containment. Fix: add a CSP (start report-only) with
`frame-ancestors 'none'`, in the server middleware and/or Caddy. Note: the app
serves user-uploaded images same-origin from `/uploads` (see L4), which raises
the value of a CSP.

### M14 (API): no graceful shutdown / WebSocket drain on SIGTERM

`crates/server/src/main.rs:264-271` calls `axum::serve(...).await` with no
`with_graceful_shutdown`. `podman stop` cuts active strategy WS/HTTP mid-flight,
dropping clients and risking incomplete writes during an update. Fix:
`with_graceful_shutdown` on SIGTERM/SIGINT; drain WS rooms with a timeout (this
also pairs with M2's persist-before-ack).

### M15 (Deploy / API): no DB connect retry; `/api/health` is process-liveness only

`crates/db/src/client.rs:422-459` connects once with no retry/backoff, so a
startup race with SurrealDB can crash-loop; `/api/health`
(`crates/site-server/src/routes/health.rs`) never touches the DB, and the
compose Surreal healthcheck is `version` only (`compose.yml:24-28`), so the
orchestrator can report "healthy" while the app cannot serve data. Fix:
retry/backoff on connect and a readiness endpoint that pings the DB.

### M16 (Deploy): `update.sh` takes no pre-update backup and has no rollback

`scripts/update.sh` pulls the image and recreates, with only a post-hoc health
check; a bad image or migration means diagnosis-by-logs, not restore. The new
image runs migrations on boot with no snapshot taken first. Fix: snapshot
(restic) or record the previous image id before recreate; document
`SITE_SERVER_IMAGE=...sha-...` rollback.

### M17 (Deploy): deploy tracks the mutable `:main` image tag; bases unpinned; no provenance/signing

`compose.yml:57` and `scripts/{install,update}.sh` default to
`ghcr.io/frozentear/scuffed-crew:main`; `Containerfile:4,26` and
`relay/Containerfile` pin bases by tag only (`rust:1.92-bookworm`,
`debian:bookworm-slim`, `dockurr/strfry:latest`, a floating relay29 clone), and
`publish-image.yml` pushes `main`/`latest`/short-sha but nothing consumes the
sha by default and there is no cosign/attestation. A silently-bad or swapped
image lands on the next pull with a weak rollback story. Fix: default to a
digest or `sha-<short>` tag, pin bases by digest, and add provenance
attestation.

### M18 (API): rate-limit default trust includes all private ranges, so a docker/NAT peer is trusted (`INCOMPLETE FIX of DR1-AUTH-001`)

`crates/site-server/src/rate_limit.rs:166-179` defaults the trusted set to
loopback plus all RFC1918/link-local ranges when `TRUSTED_PROXIES` is unset.
The server binds `0.0.0.0`; under a docker/podman bridge the peer is the bridge
gateway (a private address) and is therefore trusted, so a client-supplied
`X-Forwarded-For` is honored and a rotating XFF restores unlimited auth buckets.
The blessed host-Caddy -> `127.0.0.1` path is safe (peer is loopback and Caddy
sets XFF), but any deploy that publishes the container port without a
header-sanitizing proxy as the sole trusted hop is exposed. Fix: default trust
to loopback only and require explicit `TRUSTED_PROXIES` for docker/Caddy.

### M19 (Tracker / Deploy): in-app updater runs `main`'s bootstrap even when a tag is pinned; no signature; same-origin checksum

`crates/stat-tracker-ui/src/update.rs:23-25,408-444` downloads
`bootstrap.sh` from `.../main/...` and `bash`es it; `STAT_TRACKER_TAG` pins only
the tarball, and any `.sha256` comes from the same GitHub release asset set
(`crates/stat-tracker/dist/bootstrap.sh:5-7,197-227`). A bad merge/force-push to
`main` (short of a full compromise) changes what pinned-tag installers execute,
and the checksum provides no independent integrity. Fix: pin the bootstrap (and
`install.sh`) to the same release tag or embed the installer in the tarball;
verify a digest/signature from a separate trust root before installing.

### M20 (Tracker): sync bearer token may be sent over cleartext `http://`

`crates/stat-tracker/src/config.rs:71-117` accepts any `server_url`;
`crates/stat-tracker-ui/src/settings.rs:152-161` only requires non-empty URL +
token; `crates/stat-tracker/src/sync/mod.rs:19-36` sends `bearer_auth` with no
scheme check. A user who pastes an `http://` URL leaks the daemon token to any
network MITM. Fix: reject non-`https` (allow `http://localhost` in debug only)
and warn in Settings.

### M21 (Site): admin dashboard collapses fetch errors to "0" KPIs

`crates/app/src/pages/admin/dashboard.rs:48-90,121-157` uses
`use_api`/`use_api_list` but never reads `.error`, so a 403/500 renders as
`unwrap_or(0)` KPIs. Officers see a broken load as "no data." Residual of
`DR1-FRONT-001` (list pages were fixed via `admin_pending`; the dashboard was
not). Fix: use the shared pending/error affordance and do not treat `None` as
zero.

### M22 (Site): light-theme contrast below WCAG AA for muted text and success

`crates/app/src/theme/tokens.rs:35-50`. Measured ratios: light `--text-3`
`#83838f` on `--bg` `#f7f7f9` = 3.50 (fail); on `--surface`/`--surface-2` = 3.74
/ 3.29 (fail); light `--ok` `#0ea66e` on `--bg` = 2.93 (fail); dark
`--accent-fg` `#fff` on `#8f73ff` = 3.46 (fails AA-normal, OK for large/UI). Dark
body/muted text passes. Fix: darken `--text-3` and `--ok` in the light scope.
